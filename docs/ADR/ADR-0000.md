# ADR-0000: AI Usage Principle

- **Status:** Proposed
- **Date:** 2026-11-03
- **Decider:** Stephanie

## Context

This project is a Node and TypeScript application built to learn those technologies, using methods recommended by experts. I will refer to textbooks and the online community, and bring in my own experience as a .NET developer.

Because the project is for my own learning, its value depends on the decisions and code being mine. AI tools offer real efficiency gains, but used without limits they could produce code that looks competent while the understanding behind it isn't mine.

This policy keeps the project meaningful to me as a developer while still making use of the automation AI offers.

## Decision

### AI's role

AI is used to challenge my decisions and to help me produce better code and solutions. It acts as a sparring partner. It does not approve designs.

### How patterns become established

Patterns cover things such as where logic is written, when code is extracted into a service, and coding standards. They are established over time from:

- my own knowledge, built from study material
- feedback from AI
- lab work in a separate sandbox project

At the end of each iteration I review the patterns built so far and decide which can be automated in future. I make that decision, and I record it in `CLAUDE.md`. AI may propose patterns, but it does not agree them.

### Verification

All AI-written code is reviewed by me before it is merged.

### Boundaries

No area of the codebase is off-limits to AI by default. The controls are the review gate and the end-of-iteration review.

How AI is instructed to do only what was asked, and no more, is a working practice rather than a policy. It is documented in `CLAUDE.md`.

## Consequences

- Early iterations will be slower, because most work is paired or written by hand until patterns are established.
- Each iteration needs a short review step to decide what can be automated.
- `CLAUDE.md` becomes a living record of agreed patterns and must be kept current.
- Review is weakest where code is hardest to verify, such as time-based rules and state transitions. That risk is accepted and mitigated by tests written against the business rules.
- Anyone reading the repository can trace how AI was used and why.
